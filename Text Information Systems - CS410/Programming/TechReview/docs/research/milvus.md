# Milvus

Self-hosted notes for text retrieval. Checked against Milvus **v3.0.5** (published 2026-10-30) and the docs branch `v3.0.x` at commit `0902cf3` (2026-11-09). The live site `https://milvus.io/docs` returned 302 and then 403 from this environment, so the citations are the GitHub docs tree, not a rendered milvus.io page. Release notes were also read for v2.4.0, v2.4.0-rc.1, v2.5.0, v2.6.0, v2.6.0-rc1, v2.6.4, v3.0.0, and v3.0.1 through v3.0.5. Confidence is **partial**: several official pages disagree with each other, there is no closed-form RAM formula, and Milvus was not started.

## A. What it is and the design goal

Milvus is an open-source, cloud-native vector database for similarity search on large embedding collections, together with structured metadata. The overview presents it as the retrieval layer for retrieval-augmented generation, semantic search, and agent memory: the application supplies the data, the embedding model, and the access rules. The architecture page states the design goal as high-performance similarity search on massive vector datasets, built on Faiss, HNSW, DiskANN, and SCANN. The v3.0.5 README describes the same product as a high-performance vector database written in Go and C++, under the LF AI & Data Foundation, with Zilliz as the major contributor. ([What is Milvus](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/about/overview.md), [Architecture overview](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/reference/architecture/architecture_overview.md), [README at v3.0.5](https://github.com/milvus-io/milvus/blob/v3.0.5/README.md))

The license file at tag v3.0.5 is the Apache License, Version 2.0. ([LICENSE](https://github.com/milvus-io/milvus/blob/v3.0.5/LICENSE))

The overview says the system is column-oriented, so a query reads the fields it needs, and that the search engine is C++ with hardware-aware SIMD. Treat the “2–5x” and “30%–70% versus FAISS and HNSWLib” sentences on that page as project claims. They were not measured here. ([What is Milvus](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/about/overview.md))

The README tells researchers to cite Wang et al., “Milvus: A Purpose-Built Vector Data Management System,” SIGMOD 2021, and Guo et al., “Manu: a cloud native vector database management system,” PVLDB 2022. Those PDFs were not opened, so they are not evidence for the claims below. ([README](https://github.com/milvus-io/milvus/blob/v3.0.5/README.md))

## B. How it stores and searches

A write is validated, appended to a write-ahead log, and becomes searchable as **growing** data. When the segment fills it is sealed, then a Data Node builds an index and writes it to object storage. A search hits Streaming Nodes, which search growing data locally and ask Query Nodes to search sealed segments. Results are reduced at the segment, the streaming node, and the proxy. ([Architecture overview](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/reference/architecture/architecture_overview.md))

Current cluster architecture is four layers: stateless proxies; one active Coordinator (DDL, a timestamp oracle, streaming-service binding, query topology, compaction and index tasks); worker nodes (Streaming Node, Query Node, Data Node); and storage (etcd for metadata, object storage, and a WAL). In Woodpecker’s zero-disk mode the WAL uses object storage and the meta store and does not add another service. ([Architecture overview](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/reference/architecture/architecture_overview.md), [Main components](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/reference/architecture/main_components.md))

**Knowhere** is the vector execution engine. It sits on third-party index libraries and is called from Go via CGO. It can choose CPU or GPU. The Knowhere page still says the libraries are Faiss, Hnswlib, and Annoy, and it still describes an index node. The architecture overview says Faiss, HNSW, DiskANN, and SCANN, and the Data Node builds indexes. The current index table has no ANNOY entry. Use the architecture overview and the index table for what 3.0 ships. Treat the Knowhere page’s Annoy and index-node wording as stale. The 2.6.0-rc1 notes say IndexNode was merged into DataNode, and RootCoord, QueryCoord, and DataCoord were merged into MixCoord. The overview page still says query, data, and index nodes scale independently. That overview sentence is the stale one. ([Knowhere](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/reference/knowhere.md), [Index explained](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/indexes/index-explained.md), [v2.6.0-rc1](https://github.com/milvus-io/milvus/releases/tag/v2.6.0-rc1))

Persistent inserted data is an incremental log in object storage. Documented backends include MinIO, S3, GCS, Azure Blob, Alibaba OSS, and Tencent COS. etcd holds module metadata, not the vectors. Deletes are logical until compaction and a later garbage-collection pass. Growing segments are buffered in memory until they are persisted. Interim indexes on growing segments are on by default. ([Product FAQ](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/faq/product_faq.md))

**Multi-vector** here means several vector fields on one collection, not a ColBERT matrix. The official example uses a dense text field, a sparse text field, and an image field. The page says the default field count can be raised with `proxy.maxVectorFieldNum` up to 10. The default itself is deferred to a Zilliz Cloud wiki that was not fetched. ([Multi-vector search](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/search-query-get/multi-vector-search.md))

The limits page says a vector dimension maximum of 32,768, 64 fields per collection, `topk` and `nq` each capped at 16,384, and VARCHAR at 65,535 bytes. ([Limits](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/about/limitations.md))

## C. Deployment models

| Shape | What you run | What the docs say you do not get |
|---|---|---|
| Milvus Lite | A Python library and a local directory. No separate etcd, object store, or message queue. | Access control and binary vectors. Lite 3.x stores a directory. A Lite 2.x file needs export and migration. It is a library, not the shared server. |
| Standalone | One machine, one Docker image, embedded Woodpecker by default. | No online upgrade from Standalone to a cluster. |
| Distributed | Kubernetes. Ingestion and search on separate nodes. Woodpecker as its own service by default. | You operate proxy, coordinator, streaming, query, and data roles, plus etcd and object storage. |
| Zilliz Cloud | The managed service named by the project: Serverless, Dedicated, and BYOC. | The pages that were read do not document Zilliz internals. |

Standalone and Distributed both use a message queue, object storage, and a metadata store. A vector count alone does not set capacity. The install page says to estimate from dimensions, scalar fields, index settings, and replicas, then benchmark concurrency and write rate. Standalone adds access control and the consistency levels Strong, Bounded Staleness, Session, and Eventual. Distributed adds physical resource groups. Lite includes hybrid search, metadata filtering, partitions, and databases. ([Install overview](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/getstarted/install-overview.md), [README](https://github.com/milvus-io/milvus/blob/v3.0.5/README.md))

The 2.6 line reduced the old bill of materials. Woodpecker replaced Kafka or Pulsar as the default WAL. MixCoord replaced the three coordinators. DataNode absorbed IndexNode. That is a smaller set. It is still a database plus metadata and object storage. ([v2.6.0](https://github.com/milvus-io/milvus/releases/tag/v2.6.0), [Main components](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/reference/architecture/main_components.md))

## D. Resource characteristics

In full-load mode a QueryNode loads segment metadata, field data, and indexes at initialization. The limits page says data to be loaded must stay under 90% of the total memory of all query nodes, leaving the rest for the execution engine. No page that was read gives a closed-form RAM estimator such as bytes per vector times an HNSW multiplier. ([Tiered storage](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/storage-optimization/tiered-storage-overview.md), [Limits](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/about/limitations.md))

Three documented ways off that ceiling:

- **mmap** maps selected raw fields or indexes to disk and the OS page cache. Cache misses cost latency. Frequently used data and indexes should stay fully loaded. The 2.4.0-rc.1 notes give one example, not a current guarantee: mmap on an HNSW collection on a 2-CPU, 8 GB host loaded 4× more data with under 10% performance loss.
- **DISKANN** is an on-disk Vamana graph plus an in-memory product-quantization sketch, for collections that do not fit in RAM. The index guide says mmap is the wrong tool when most data is on disk, and DiskANN is the latency choice in that case.
- **Tiered storage**, documented for 2.6.4 and later, loads only segment metadata at start, pulls field data by chunk and indexes by whole segment on demand, and evicts cache with LRU. Object storage remains the copy of record. Cold queries can be slower. Full-load is the latency-sensitive choice. A QueryNode that shares its disk or memory with other workloads can still run out of resources. The 2.6.4 notes that were scanned do not themselves use the words “tiered storage.” The version gate comes from the docs page.

The storage-disaggregation page still says Milvus “plans to implement” cold/hot separation. That sentence conflicts with the tiered-storage guide and the architecture overview, which describe tiered storage as already available. Prefer the latter two. ([mmap](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/search-query-get/mmap.md), [DISKANN](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/indexes/floating-vector/diskann.md), [Tiered storage](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/storage-optimization/tiered-storage-overview.md), [v2.4.0-rc.1](https://github.com/milvus-io/milvus/releases/tag/v2.4.0-rc.1))

The index guide includes a worked memory estimate for 1,000,000 vectors of 128 dimensions and 2,000 IVF clusters: centroids 1.0 MB, assignments 2.0 MB, PQ with 8 subquantizers 8.0 MB (11.0 MB with no refinement), SQ8 128 MB. “IVF-PQ + 10% raw refinement” is given as 62.2 MB. These are arithmetic examples, not a benchmark. The same section says graph indexes such as HNSW carry more per-vector overhead than IVF. Scalar quantization SQ8 is described as one byte per dimension, “75%” less memory than float32. Product quantization’s example compression is “4–32x,” with lower recall. ([Index explained](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/indexes/index-explained.md))

HNSW parameters in the same tree: `M` default 30, range [2, 2048]. Larger `M` raises accuracy, memory, and insert time. `efConstruction` default 360. Search `ef` should be at least `limit` for an ordinary kNN query. ([HNSW](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/indexes/floating-vector/hnsw.md))

CPU: the performance FAQ says index builds and queries raise CPU use, and that query CPU follows `nq` and `nprobe`. Inserts are described as not CPU-intensive, while a segment under the index threshold (it names `rootcoord.minSegmentSizeToEnableIndex`, default 1024 rows) is searched brute-force and can slow queries. The same answer says Annoy is single-threaded. Annoy is absent from the current index table, so that clause looks leftover. v3.0.1 separately notes a single-threaded default for growing-segment interim index builds. ([Performance FAQ](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/faq/performance_faq.md), [v3.0.1](https://github.com/milvus-io/milvus/releases/tag/v3.0.1))

A collection must be loaded before search or query. That load step is the documented cold-start analogue. Inserts after load are indexed and loaded automatically. ([Load and release](https://github.com/milvus-io/milvus-docs/blob/v3.0.x/site/en/userGuide/collections/load-and-release.md))

## E. Hybrid search

Hybrid search runs several ANN searches at once, one per vector field, including a dense field and a sparse field, then reranks. Every vector field used in the request needs an index and must be loaded. ([Multi-vector search](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/search-query-get/multi-vector-search.md))

**BM25** is a built-in function over sparse vectors. Raw text is analyzed, the function writes a sparse vector, and search sends plain text. The index example is `SPARSE_INVERTED_INDEX` with metric `BM25`, `inverted_index_algo` `DAAT_MAXSCORE`, `bm25_k1` 1.2, and `bm25_b` 0.75. The BM25 page describes the score as, per matched term, IDF times a saturated term-frequency boost controlled by `k1`, times a length normalization controlled by `b`. The document score is the sum of those term scores. No external embedding model is required for this path. Learned sparse vectors such as SPLADE and BGE-M3 are a separate path: the caller supplies the sparse vector. ([Full text search](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/search-query-get/full-text-search.md), [BM25 function](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/embeddings-reranking/embedding-function/bm25-function.md))

**RRF** ignores raw distances. The worked example sets smoothing constant `k` to 60 and scores a hit as the sum of `1/(k+rank)` over the lists it appears in. Rank 1 contributes 1/61 when `k` is 60. Default `k` is 60, allowed range (0, 16384), recommended band [10, 100]. The hybrid-search code sample passes `k` 100. Both numbers are in the current docs. Neither is a measured optimum. v3.0.1 adds a weighted RRF variant with optional per-request weights. ([RRF ranker](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/embeddings-reranking/reranking/rrf-ranker.md), [v3.0.1](https://github.com/milvus-io/milvus/releases/tag/v3.0.1))

**Weighted Ranker** collects each path’s scores, maps them with `arctan` into `[0, 1]` because IP and L2 are not comparable, multiplies by a per-path weight in `[0, 1]`, and ranks those weighted scores. The prose does not write an explicit sum. The numeric example multiplies displayed scores and does not show an arctan step. Treat that example as illustrative arithmetic. Weights do not have to sum to 1. A later comment uses 0.8 and 0.3. ([Weighted ranker](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/embeddings-reranking/reranking/weighted-ranker.md))

**Unresolved.** The limits table says hybrid search on `SPARSE_INVERTED_INDEX` supports only `RRFRanker`. The weighted-ranker and hybrid-search guides describe Weighted Ranker for multi-vector search without that restriction. Those pages were not reconciled. The same limits page lists one index per collection, which conflicts with multi-vector search requiring an index per vector field. ([Limits](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/about/limitations.md), [Weighted ranker](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/embeddings-reranking/reranking/weighted-ranker.md))

A minimal official example is `MilvusClient.hybrid_search` on two `AnnSearchRequest`s, one with the string `"modern dining table"` and one with a prepared embedding, each `limit` 10, and `ranker=RRFRanker(k=100)`, outer `limit` 10. The collection is assumed to already exist. ([RRF ranker](https://github.com/milvus-io/milvus-docs/blob/v3.0.x/site/en/userGuide/embeddings-reranking/reranking/rrf-ranker.md))

## F. Metadata filtering and multi-tenancy

Filtered search has two documented modes. **Standard filtering** applies the boolean expression first, then runs ANN on the survivors. **Iterative filtering** walks vector hits and tests the scalar predicate until top-K is filled. The guide says that helps complex expressions and can hurt when many entities fail the filter. A query, as opposed to a search, is scalar filtering only, with no vector metric. ([Filtered search](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/search-query-get/filtered-search.md), [Product FAQ](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/faq/product_faq.md))

The index guide’s filter-ratio heuristic: under 85% filtered out, prefer graph indexes; 85–95%, IVF; over 98%, brute-force FLAT. The next sentence says those rules are not always correct and that recall should be tuned per index on the operator’s data. Treat the percentages as a heuristic. ([Index explained](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/indexes/index-explained.md))

Scalar indexes exist so those filters are not scans. The index table recommends INVERTED for VARCHAR (also BITMAP and Trie), BITMAP for bool, INVERTED or STL_SORT for integers, and INVERTED for floats and JSON. The scalar-index page says inverted indexes are Tantivy-based. ([Index explained](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/indexes/index-explained.md), [Scalar index](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/reference/scalar_index.md))

**Tenancy is four strategies on one cluster.**

| Strategy | Documented scale | Isolation |
|---|---|---|
| Database | Default cap 64 (`maxDatabaseNum`) | Physical isolation, separate schemas, RBAC. No cross-tenant search. |
| Collection | Default cap 65,536 (`maxCollectionNum`) | Physical isolation and RBAC. |
| Partition | 1,024 tenants per collection | Shared schema. No partition-level RBAC. Cross-tenant search is allowed. A search can name partitions, and only loaded partitions can appear. |
| Partition key | “Millions” of tenants | A scalar field is hashed into a set of physical partitions. The multi-tenancy page says 16 physical partitions, with many tenants per partition. Shared schema. No RBAC on the key. Cross-tenant search is allowed. The page says hot/cold handling is not supported for this strategy. |

The page’s own order for scale is partition key, then partition, then collection, then database. A filter on the partition key prunes to the matching partitions. The guide recommends a scalar index on the key because, without it, every entity in the touched partitions is scanned. Partition-key isolation builds a separate index per key value and, on search, uses only that sub-index. The filter must name exactly one key value. The guide says this currently applies only when the vector index is HNSW. ([Multi-tenancy](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/reference/multi_tenancy.md), [Partition key](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/search-query-get/use-partition-key.md))

**Another limits conflict.** The limits page lists insert, search, and query RPC payloads at 64 MB. The product FAQ says an insert must not exceed 1,024 MB because of gRPC. Both are current docs pages. The enforced cap was not checked in server code. ([Limits](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/about/limitations.md), [Product FAQ](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/faq/product_faq.md))

## G. Notable changes, 2024–2026

**2024, Milvus 2.4.0** (17 April 2024), keeping the 20 March release-candidate set. Sparse vectors (beta) for SPLADE, BGE-M3, and externally computed BM25, searched with maximum inner product. Multi-vector search with RRF and average weighted scoring. Grouping search for passage-to-document RAG. Tantivy inverted indexes and prefix, infix, and suffix match. float16 and bfloat16 vectors. GPU CAGRA. GA notes add scalar AutoIndex and say grouping search was dropped for binary vectors and for hybrid search. ([v2.4.0-rc.1](https://github.com/milvus-io/milvus/releases/tag/v2.4.0-rc.1), [v2.4.0](https://github.com/milvus-io/milvus/releases/tag/v2.4.0))

**2024-12-23, Milvus 2.5.0.** In-server Sparse-BM25, so inserts and queries can be raw text, with Tantivy analyzers and BM25 stats updated on insert. Text match as a filter. Bitmap indexes. Nullable scalars and defaults. HNSW moved from hnswlib to Faiss, plus HNSW SQ, PQ, and PRQ. Clustering compaction (beta). The notes say the Streaming Node was beta and would be official in 3.0. The later 2.6.0-rc1 notes say it became GA in 2.6. The later note matches the shipped architecture. ([v2.5.0](https://github.com/milvus-io/milvus/releases/tag/v2.5.0), [v2.6.0-rc1](https://github.com/milvus-io/milvus/releases/tag/v2.6.0-rc1))

**2025-08-06, Milvus 2.6.0**, building on the 14 June 2025 release candidate. Streaming Node GA. Woodpecker replaces Kafka and Pulsar as the default WAL. MixCoord. DataNode absorbs IndexNode. Phrase match. MinHash LSH (beta). Time-decay rerankers. Lindera and ICU tokenizers. Embedding functions that call an external model so inserts and queries can be raw text. RaBitQ. JSON path indexes. INT8 vectors. A lazy cache “for datasets larger than memory.” Storage format v2 is described with project-reported upper bounds (up to 100× versus the previous Parquet path, up to 98% fewer files, compaction memory reduced by 300%, read I/O up to 80%, write I/O more than 600%). Those are release-note figures. Direct upgrade from the release candidate is unsupported. ([v2.6.0](https://github.com/milvus-io/milvus/releases/tag/v2.6.0))

**2026-07-29, Milvus 3.0.0.** TEXT fields for long text (`text_match`, `phrase_match`, BM25), with values under 64 KB stored inline and larger values in LOB files, only when Storage V3 (Loon) is turned on with `common.storage.useLoonFFI`. That switch is off by default, and enabling it blocks rollback to 2.6. New sparse algorithms (SINDI, Block-Max WAND, Block-Max MaxScore) are also opt-in. The notes say that once enabled, SINDI is the default for sparse inner product and MaxScore is the default for BM25. They report an internal result: the compressed BM25 index about 3× smaller than the 2.6 sparse index at comparable recall, and SINDI up to about 10× the QPS of MaxScore on learned sparse embeddings. Also online add, backfill, and drop of columns, including attaching BM25 to an existing collection. v3.0.5 (30 October 2026) does not flip Storage V3 on by default. v3.0.3 adds Function Chain on hybrid search. v3.0.4 adds lazy Storage V3 column-group loading, off by default. ([v3.0.0](https://github.com/milvus-io/milvus/releases/tag/v3.0.0), [v3.0.5](https://github.com/milvus-io/milvus/releases/tag/v3.0.5))

RaBitQ’s own index page was not read, so this note does not describe the algorithm.

## H. Strengths and limitations for text retrieval

**Strengths**

- Dense vectors, built-in BM25, and learned sparse vectors can live in one collection and be fused with a named ranker.
- Scalar filters, partitions, and a partition key cover a wide range of tenant counts, with RBAC at the database and collection layers.
- The 2.4 through 3.0 line is specifically about text: analyzers, phrase and term match, grouping, decay functions, and long TEXT.
- There is a path from one Docker machine to a Kubernetes cluster, and a named managed service with the same data model.
- DiskANN, mmap, and tiered storage are documented exits when the collection does not fit in query-node RAM.

**Limitations**

- Even Standalone is a database plus metadata and object storage. Distributed adds several node roles. Lite is the single-process exception, and it is a library.
- Standalone cannot be upgraded online into a cluster.
- The default full-load path is RAM-capped at 90% of query-node memory, and the docs refuse a count-only sizing rule.
- VARCHAR is 65,535 bytes unless TEXT plus opt-in Storage V3 is used. Storage V3 and the new sparse indexes are off by default on 3.0.5, and turning Storage V3 on blocks rollback to 2.6.
- BM25 quality depends on the analyzer. Default fusion is rank fusion or a normalized-score mix. A cross-encoder is a separate, optional model ranker.
- Several official pages disagree: the Knowhere page versus the architecture overview, the limits table versus hybrid search, the 64 MB versus 1,024 MB insert cap, and the “plans to implement” storage sentence versus tiered storage. A review should not quote a single limits table as complete.

([Multi-vector search](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/userGuide/search-query-get/multi-vector-search.md), [Install overview](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/getstarted/install-overview.md), [v3.0.0](https://github.com/milvus-io/milvus/releases/tag/v3.0.0), [Limits](https://github.com/milvus-io/milvus-docs/blob/0902cf3ff17c4a5629c075a5f5cc0452f9a0f368/site/en/about/limitations.md))

For an 8–12 minute review, demo Standalone, name RRF as the fusion to show first because the score ranges are not comparable, and spend a minute on the bill of materials: etcd, object storage, query-node RAM, and the 90% load ceiling. Mention Zilliz Cloud as the managed alternative. Leave Distributed, Lite, and the 3.0 lakehouse features for a question. Lite is a prototype library. Distributed is justified when one server’s RAM or availability is the limit.
