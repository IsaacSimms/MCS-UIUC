# CS425: Week 12 — Distributed file systems, distributed shared memory, and sensor networks

This week is three "back to basics" topics that look unrelated, but they share one question: when you hide the network behind a familiar interface (a file, a memory page, a tiny event-driven OS), what do you give up? Every design choice below is a trade between how transparent the system looks and how much consistency, statefulness, or energy it costs to keep up that illusion. The syllabus readings are Coulouris 5th ed. Chapter 12 (12.2 file service architecture, 12.3 NFS, 12.4 AFS) and §6.5 "Shared memory approaches" ([CDK5 contents](https://www.cdk5.net/contents)). The FA2026 lecture decks are still marked tentative, so these notes follow the FA2025 decks L24.A, L25.A, and L25.B, plus the original papers.

## The "Vanilla DFS" and why statelessness matters

The lecture builds a toy DFS before showing real ones (L24.A). It has three parts. A flat file service on the server reads and writes by `file_id`. A directory service maps names to ids. A client service glues the two together. The detail that shows up on quizzes is the flat file API: `read(file_id, buffer, position, num_bytes)` takes an **absolute position** and uses **no file descriptor**. Both choices come from one goal. An absolute position makes the call **idempotent**, so the client can use at-least-once retry semantics. No descriptors means the server is **stateless**, so recovering from a crash requires restoring nothing. Unix `read`/`write` are neither: they move a hidden read-write pointer, so a retried call reads or writes the wrong bytes.

Keep the at-most-once versus at-least-once distinction clear. Idempotent operations (a read at an absolute offset) can safely be retried. Non-idempotent ones (an append) cannot. Real systems pay for confusing the two. When Howard et al. benchmarked NFS at a load of 10 or more, workstations failed with file system errors because NFS's datagram RPC retried non-idempotent calls after lost replies ([Howard et al. 1988](https://www.cs.cmu.edu/~satya/docdir/howard-tocs-afs-1988.pdf), §5). Also notice that L24.A separates authentication (who you are) from authorization. Authorization comes as access control lists (per file, which users may do what) or capability lists (per user, which files they may touch).

## NFS: stateless server, cached clients, a freshness window

Sandberg et al. say plainly that "NFS uses a stateless protocol." Each call carries everything it needs, and a client that gets no answer simply retries until the server comes back ([Sandberg et al. 1985](https://www.cs.ucf.edu/~eurip/papers/sandbergnfs.pdf)). The price is on writes: because the server is stateless, it "must commit any modified data to stable storage before returning results," which also means flushing the indirect blocks and the inode. The paper names synchronous writes as the slow operation. The file handle is (filesystem id, inode number, inode generation number). The generation number keeps a stale handle from silently pointing at a reused inode.

On the client, the Virtual File System (VFS) layer is what delivers transparency. Processes keep using ordinary descriptors, and the v-node for each open file points either at a local inode or at a remote NFS server (L24.A). The lecture asks a trick question: if processes use file descriptors, is NFS still stateless? Yes. The descriptor state lives in the client kernel, while the server sees only handles and absolute offsets.

The formula to know is client cache validation. Each cached block carries **Tc** (when the client last validated it) and **Tm** (when the server last modified it). At time T the entry is valid if (T − Tc < t) or if Tm_client = Tm_server, where t is the freshness interval. Solaris adapts t between 3 and 30 seconds for files and between 30 and 60 seconds for directories (L24.A). So NFS gives you only bounded staleness. Another client's write can stay invisible to you for up to t seconds. The server side has the same trade: a delayed write (flushed every 30 seconds) is fast but not consistent, and write-through is consistent but slow.

## AFS: whole files, callbacks, and close-to-open

AFS turns NFS's design around, based on measured workload assumptions. Most files are small, most accesses come from a single user, reads far outnumber writes, and access is usually sequential (L24.A). So **Vice** (the server) ships the **whole file** to **Venus** (the client). Venus caches it on local disk, where it survives reboots. Reads and writes are applied to that local copy, and changes go back to Vice only on **close**. The result is close-to-open consistency with last-closer-wins behavior, not one-copy semantics.

The key mechanism is the **callback promise**. Instead of checking with the server on every open, "Venus now assumes that cache entries are valid unless otherwise notified" ([Howard et al. 1988](https://www.cs.cmu.edu/~satya/docdir/howard-tocs-afs-1988.pdf), §3.1). Before allowing another client's modification, the server breaks the callback. The paper admits the cost directly. The server now holds per-client state, rebooted clients must treat every cached entry as suspect, and the two sides' callback state can drift. Look at the contrast: NFS buys crash simplicity by being stateless, and AFS buys scalability by accepting server state. The numbers justify it. NFS edges out Andrew at low load, but the crossover comes around load 3–4. At load 18, NFS server CPU saturates at 100% while Andrew sits near 38–42% (Howard et al., §5).

FA2026 also lists GFS under this lecture. Read it as the datacenter answer to a different workload. It uses a single master for metadata, 64 MB chunks, leases that pick a primary replica to order mutations, and **record append**, which writes data "at least once atomically," so readers must tolerate duplicates and padding ([Ghemawat et al. 2003](https://static.googleusercontent.com/media/research.google.com/en//archive/gfs-sosp2003.pdf), §2.4–2.5, §3.3). That makes three DFSs with three different answers to "what does a reader see after a concurrent write?"

## DSM: paging over the network

Distributed shared memory turns message passing inside out. Processes read and write shared pages, a page fault traps into DSM software, and that software fetches the page over the network. Each abstraction can be built on top of the other (L25.A). Coulouris treats it in §6.5 as one form of indirect communication. The lecture's invalidate protocol is a small state machine you should be able to replay from memory. Each page is in state **R** (any number of read copies, no writers) or **W** (only the owner holds a copy), and there is exactly one **owner**, the process with the latest version.

The cases graders like are the ones where you might be tempted to skip messages. A non-owner holding an R copy can read locally, since no W copy can exist. A reader who lacks the page while someone holds it in W must ask that holder to **degrade** to R before taking a copy. Simply copying it would let the writer keep writing behind your back. An owner holding R who wants to write still has to **multicast invalidations** to the other R holders before switching to W. Being owner does not mean being the only holder. A writer with no copy invalidates everyone, fetches the latest copy, and becomes the owner (L25.A).

**False sharing** is the main gotcha. Two processes writing unrelated variables on the same page make the page ping-pong between them under invalidate. Page size is the knob. Too large gives false sharing, and too small gives too many transfers. Li and Hudak's IVY prototype found about 1 KB to be a good compromise and noted that "the right size is clearly application dependent" ([Li & Hudak 1989](https://people.eecs.berkeley.edu/~prabal/resources/osprelim/LH89.pdf), §2). The alternative is the **update** protocol: many W holders, each write multicast to the others. It wins when sharing is heavy, writes are small, and pages are large, but invalidate is the usual default. If you want to know how a faulting node finds the owner without the lecture's multicast, read Li and Hudak's dynamic distributed manager. Each node keeps a `probowner` hint and forwards the request along a chain of hints to the true owner (§5.3). DSM can use any consistency model from earlier in the course, from linearizability down to eventual. L25.A closes by asking whether RDMA will revive DSM.

## Sensor networks: energy is the scheduler

L25.B describes the canonical mote: a sensor, a microprocessor, a radio, and a battery. The MICA example has a 4 MHz CPU, a 40 kbps radio, 4 KB of SRAM, and about 7 days of battery at full activity on two AA cells. The fact the lecture builds on is the power budget. Transmitting on the radio costs about 12 mA, while an active CPU costs about 4.6 mA, so it is **cheaper to compute than to transmit**. That leads directly to **in-network aggregation**. Nodes form a tree rooted at the base station, and internal nodes send summaries (sums, counts, averages) instead of raw readings (L25.B). Nodes also fail often, so the protocols must be self-organizing and self-healing and must scale in message count.

TinyOS is the OS side of the same constraint. The paper reports a 178-byte footprint and two-level scheduling ([Hill et al. 2000](https://pdos.csail.mit.edu/archive/6.097/readings/tinyos.pdf)). Its execution model is worth getting exactly right. **Commands** are non-blocking requests sent downward. **Events** come from hardware and propagate upward, and commands cannot signal events, which prevents cycles. **Tasks** do the real work and run to completion with respect to other tasks, though events can preempt them, so a single stack suffices. Tasks "must never block or spin wait." Allocation is static only. You write applications in nesC as modules wired together by configurations (L25.B).

## Programming tips

These lectures have no MP of their own, but the ideas carry over to the C++ emulator code. If your message handlers can be retried or duplicated, make them idempotent: key each update by an absolute value (a heartbeat counter or version number), not by "add one." Treat any cached view (a membership list, a replica's value) like an NFS cache entry with a freshness timestamp. TinyOS's rule that tasks never block is the same reason the emulator's per-tick `nodeLoop` work must return quickly. ## For the podcast

The listener is an MCS student already in CS425 who has seen consistency models, RPCs, and replication, so don't explain caching or what a file is. Spend most of the time on the NFS-versus-AFS contrast (stateless with polling versus stateful with callbacks, plus the load-18 CPU numbers) and on walking through the DSM invalidate cases one at a time. Keep sensor hardware specs and the transistor-counting slide brief. Say "Vice" and "Venus" clearly as the AFS server and client, "TinyOS" and "nes-C" for nesC, "IVY" for Li and Hudak's system, and "Howard et al." for the AFS paper. Read the NFS freshness rule aloud as "a cached block is fine if you checked it less than t seconds ago, or if its modification time still matches the server's," then say Solaris uses three to thirty seconds for files. Describe the DSM states as "R means many readers, W means one owner writing alone." Correct these misconceptions: NFS is not strongly consistent (it is bounded-stale); AFS does not push writes as they happen (only on close); owning a DSM page in R state does not let you write without invalidating; idempotent does not mean read-only (an absolute-offset write is idempotent); and in sensor nets, the radio, not the CPU, drains the battery.
